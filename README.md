# Архитектура проекта: Голосовой ассистент для задач и встреч

Проект: Голосовой ассистент (монолит на Python).
Прототип реализован: голос и текст, четыре обязательных сценария, хранение записей в БД,
напоминания по времени и три интерфейса (Telegram, MAX, веб).
Ниже — инструкция по запуску, описание архитектуры и зон ответственности каждого участника.

---

## 🛠 Выбранный стек технологий
- **Архитектура:** Монолит
- **Язык:** Python
- **Распознавание речи (STT):** Vosk — офлайн, официальный Python-биндинг [alphacep/vosk-api](https://github.com/alphacep/vosk-api)
- **Синтез речи (TTS):** SaluteSpeech через Cloud.ru Foundation Models (реальный голос), офлайн-резерв espeak-ng
- **Нейросеть (LLM):** GigaChat API (с вызовом тулзов / Function Calling)
- **База данных:** PostgreSQL
- **ORM & Миграции:** SQLAlchemy + Alembic
- **Кэш:** Redis (кэширование основных запросов)
- **Веб-фронтенд:** React 19, TypeScript, Vite, Tailwind CSS v4
- **Интерфейсы:**
  - Веб-интерфейс
  - Telegram-бот
  - Бот в MAX

## 🚀 Быстрый старт

### 1. Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cd frontend && pnpm install && pnpm build && cd ..

cp .env.example .env
# чтобы не поднимать PostgreSQL и Redis, в .env достаточно указать:
#   DATABASE_URL=sqlite+aiosqlite:///./gorkycode.db
#   CACHE_ENABLED=false

python main.py
```

Приложение поднимает веб-интерфейс на `http://localhost:8000`, страница чата — `/`.
SQLite и отключённый Redis позволяют запустить сервис без инфраструктуры, но ответы строит
GigaChat: пока не задан `GIGACHAT_CREDENTIALS`, на каждый запрос приходит сообщение
«GigaChat не настроен…», а в лог пишется предупреждение.

Для разработки фронтенда: `cd frontend && pnpm dev` — Vite поднимается на
`http://localhost:5173` и проксирует `/api` и `/ws` на приложение. Production-сборка
(`pnpm build`) кладётся в `frontend/dist`, её раздаёт FastAPI.

### 2. Голос

Нужен `ffmpeg` в системе и модель Vosk:

```bash
curl -L https://alphacephei.com/vosk/models/vosk-model-small-ru-0.22.zip -o /tmp/vosk.zip
unzip -q /tmp/vosk.zip -d models/
```

Голосовые сообщения принимаются в Telegram, MAX и в веб-интерфейсе (кнопка записи).
Распознавание выполняет официальный Python-биндинг Vosk из
[alphacep/vosk-api](https://github.com/alphacep/vosk-api) (`vosk==0.3.45`): файлы и живой поток
идут через один и тот же `KaldiRecognizer`.
Веб-клиент стримит PCM 16 кГц по WebSocket `/ws/voice`: Vosk распознаёт чанки по мере речи,
поэтому финальный текст готов к моменту окончания записи. При недоступности WebSocket
клиент откатывается на отправку файла в `/api/voice`.
Без модели текстовые сценарии продолжают работать, на голос ассистент отвечает просьбой
написать текстом.

### 3. GigaChat и SaluteSpeech

* `GIGACHAT_CREDENTIALS` — Authorization key из кабинета developers.sber.ru (scope `GIGACHAT_API_PERS`).
* `CLOUD_TTS_API_KEY` — ключ Cloud.ru Foundation Models: через него работает SaluteSpeech
  (`wss://foundation-models.api.cloud.ru/v1/realtime`, модель `GigaChat/SaluteSpeech`, голос `Mer-Operator`).
* `SBER_TTS_CREDENTIALS` — прямой gRPC-ключ SaluteSpeech (scope `SALUTE_SPEECH_PERS`), резервный путь
  при `TTS_BACKEND=sber`; `TTS_BACKEND=local` оставляет офлайновый espeak-ng.
* Для запросов к API Сбера нужен корневой сертификат Минцифры: установите его в систему либо
  укажите `SBER_CA_BUNDLE=/путь/к/сертификату.pem`. `GIGACHAT_VERIFY_SSL=false` — только для отладки.
* Миграции: `alembic upgrade head` (или `AUTO_CREATE_TABLES=true` для локального запуска).

### 4. Авторизация по email (новое)

В обычном браузере чат доступен только после подтверждения email одноразовым кодом. Для отправки писем настройте `RESEND_API_KEY`, `EMAIL_FROM` (адрес на подтверждённом домене Resend) и отдельный случайный `EMAIL_CODE_SECRET` в `.env`. Подробная инструкция с командами и описанием изменённых файлов находится в [`EMAIL_AUTH_IMPLEMENTATION_RU.md`](EMAIL_AUTH_IMPLEMENTATION_RU.md).

Чтобы привязать Telegram, VK или MAX к аккаунту с тем же email, напишите боту `/email адрес@example.com`, а затем отправьте код из письма командой `/emailcode адрес@example.com 123456`.

### 5. Полный стек (PostgreSQL + Redis + приложение)

```bash
cp .env.example .env   # заполните токены ботов и API
docker compose up --build
```

Контейнер приложения при старте применяет миграции Alembic и скачивает модель Vosk.
Образ собирается в два этапа: Node-стадия выполняет `pnpm build`, готовая SPA попадает
в `frontend/dist` внутри контейнера.

### 6. Тесты

```bash
pip install -r requirements-dev.txt
pytest -q

cd frontend && pnpm test
```

## ✅ Что реализовано

Четыре обязательных сценария работают в каждом интерфейсе:

1. Создание задачи или напоминания — «Напомни завтра в 10 позвонить Ивану».
2. Создание встречи — «Добавь встречу с командой завтра в 15:00»; без времени ассистент
   задаёт уточняющий вопрос и не создаёт запись.
3. Список записей за период — «Что у меня сегодня?», «Что запланировано на эту неделю?».
4. Поиск старых записей — «Найди задачу про презентацию», «Когда у меня была встреча с Иваном?».

Дополнительно:

* изменение и удаление записей, отметка выполненной;
* предупреждение о конфликте встреч (в это же время уже есть встреча);
* контекст диалога: последние реплики хранятся в Redis и передаются в LLM;
* напоминания по времени через планировщик, доставляются в Telegram, ВКонтакте и MAX;
* кэширование списков событий в Redis с инвалидацией при записи;
* кнопки быстрого доступа в Telegram;
* потоковое распознавание речи в веб-интерфейсе: чанки аудио уходят в `/ws/voice`,
  промежуточный текст показывается во время речи;
* карточки действий в чате: тип, время и статус записи, кнопка «выполнено» — в веб-интерфейсе,
  Telegram и MAX (inline-кнопка в боте).

HTTP API веб-интерфейса:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/` | страница чата (React SPA) |
| GET | `/api/meta` | часовой пояс и быстрые действия для интерфейса |
| POST | `/api/chat` | текст: `{"text": "...", "client_id": "...", "speak": false, "closing": false}`; `speak: true` возвращает озвучку ответа, `closing: true` — прощание вместо создания события |
| POST | `/api/chat/warmup` | прогрев модели системным промптом до первой реплики (`{"status": "ok", "warmed": true}`) |
| POST | `/api/voice` | аудио: multipart `audio` + `client_id` |
| GET | `/api/events?client_id=...&period=today\|tomorrow\|week\|all` | список записей |
| POST | `/api/events/{id}/complete?client_id=...` | отметить выполненной |
| WS | `/ws/voice?client_id=...` | потоковое распознавание: PCM 16 кГц, `{"type":"stop"}`, события `partial`/`final`/`error` |
| POST | `/api/auth/session` | вход из приложения: `{"platform": "telegram\|max\|vk\|web", "payload": "...", "client_id": "..."}` → токен, личность, привязанные платформы |
| GET | `/api/auth/me` | текущая личность по токену сессии |
| POST | `/api/auth/code` | одноразовый код привязки аккаунта |
| POST | `/api/auth/link` | `{"code": "..."}` — привязать текущую платформу к аккаунту бота |
| GET | `/healthz` | проверка живости |

Запросы к API принимают `Authorization: Bearer <token>`; без заголовка они работают
по `client_id`, как раньше, — так веб-версия остаётся доступной без мини-приложения.

### Интерфейсы и вход

Ассистент работает в четырёх местах, и во всех это один и тот же аккаунт:

| Интерфейс | Реализация |
| --- | --- |
| Telegram-бот `@hackathon_helperbot` | aiogram, long polling, текст и голосовые |
| ВКонтакте `@hackathon_helperbot` | vkbottle, Long Poll, текст и голосовые |
| MAX | собственный клиент Bot API, long polling |
| Веб и мини-приложения | React SPA + FastAPI |

Мини-приложения Telegram, ВКонтакте и MAX открывают один и тот же SPA. Приложение
определяет платформу, забирает launch-данные (Telegram `initData`, MAX WebApp
`initData`, VK `vk_*` вместе с `sign`) и меняет их на подписанный токен сессии:

* Telegram — HMAC-SHA256 от `initData` с ключом из токена бота;
* MAX — та же схема с ключом `WebAppData`, как в MAX Bridge;
* ВКонтакте — HMAC-SHA256 подписи `sign` с секретом мини-приложения.

Подпись и срок жизни launch-данных проверяет `app/services/auth/launch.py`, токен
сессии выпускает `app/services/auth/tokens.py`. Привязка аккаунтов: `/link` в любом
боте выдаёт одноразовый код на 15 минут; код вводится в приложении или приходит в
мини-приложение параметром `startapp`, после чего платформенная личность
привязывается к аккаунту, а история переезжает в него
(`app/repositories/account_repository.py`). Готовые ссылки мини-приложений с кодом
возвращает `/api/auth/code`. Новые переменные окружения перечислены в `.env.example`.

Что нужно включить на стороне платформ:

| Интерфейс | Что требуется |
| --- | --- |
| Telegram-бот | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`; меню-кнопка ставится через Bot API, домен мини-приложения подтверждается в BotFather |
| Telegram-мини-приложение | `WEB_PUBLIC_URL` и `MINI_APP_PUBLIC_URL` с https; домен регистрируется в BotFather (Mini App) |
| MAX-бот | `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME` |
| MAX-мини-приложение | мини-приложение, привязанное к боту в кабинете MAX; открывается как `?startapp=<код>` |
| ВК-бот | `VK_BOT_TOKEN` с правами «Сообщения сообщества» и «Управление сообществом», в сообществе включён Long Poll API |
| ВК-мини-приложение | `VK_MINI_APP_ID`, `VK_MINI_APP_SECRET` — без них проверка подписи недоступна и вход из ВК идёт по коду из бота |

## 🧩 Как устроен пайплайн

`аудио → AudioConverter (16 кГц WAV) → Vosk → AssistantService → GigaChat (function calling) →
ToolExecutor → EventRepository → ответ → SaluteSpeech → аудио`

* `AssistantService` — единственная точка входа для интерфейсов: строит ответ через GigaChat,
  ведёт историю диалога и синтез речи.
* `ToolExecutor` выполняет вызовы инструментов над репозиториями одного пользователя.
  Инструменты: `create_task`, `create_meeting`, `list_events`, `search_events`, `update_event`,
  `complete_event`, `delete_event`.
* `EventRepository` отдаёт выборки по периоду и поиск по названию/описанию с учётом словоформ.
* `ReminderService` — asyncio-цикл, который выбирает созревшие напоминания и передаёт их
  нотификаторам интерфейсов; `reminder_sent_at` защищает от повторной доставки.

Даты в БД хранятся в UTC без часового пояса, в человеческий вид переводятся в `app/core/timeutils.py`
по `TIMEZONE` (по умолчанию `Europe/Moscow`).

## 💡 Решения, принятые самостоятельно

* **Без демо-разборщика.** Единственный путь ответа — GigaChat с function calling: прототип
  не подменяет модель регулярками, а без токенов возвращает сообщение о настройке.
* **Семь инструментов вместо четырёх.** Исходное описание перечисляло создание, список и поиск;
  добавлены изменение, отметка выполнения и удаление — это закрывает бонусные сценарии.
* **Redis как хранилище истории диалога.** Кэш списков событий и история реплик живут в одном
  сервисе; при недоступности Redis он переключается на память процесса, приложение не падает.
* **Напоминания на asyncio, без APScheduler.** Для одной задачи планировщика хватает цикла с
  настраиваемым интервалом — меньше зависимостей и предсказуемое поведение.
* **Поиск по словоформам.** Запрос разбивается на слова, отбрасываются служебные, к каждому
  слову добавляются усечённые варианты и варианты с заглавной буквы (ILIKE), поэтому «Иваном»
  находит «встреча с Иваном», а «презентацию» — «подготовить презентацию».
* **Длительность встречи** хранится строкой в описании: отдельная колонка не понадобилась.

## 🔭 Ограничения и что улучшил бы дальше

* Vosk small-модель путает имена и термины; для качества нужен больший офлайн-модель.
  Потоковое распознавание работает в вебе, боты по-прежнему присылают файл целиком.
* Надёжность function calling зависит от GigaChat: цикл ограничен четырьмя итерациями, при
  ошибке инструмента ассистент задаёт уточняющий вопрос; если модель падает уже после
  выполнения действия, пользователь получает результат действия, а не сообщение об ошибке.
* Веб-канал не получает push-напоминания: нотификаторы зарегистрированы только для Telegram и
  MAX. Напоминание, созданное в вебе, видно в списке, но уведомление по нему не приходит.
* Повторяющиеся события, интеграция с настоящим календарём и семантический поиск (эмбеддинги)
  не реализованы — поиск сейчас подстрочный с учётом словоформ.
* Веб-клиент идентифицируется `client_id` из localStorage: для нескольких пользователей нужна
  настоящая аутентификация.
* Нет метрик и трассировок: добавление OpenTelemetry и кэша синтеза речи — следующие шаги.
* MAX использует long polling (для production нужен webhook), Telegram — polling.
* Конфликт встреч только обнаруживается и озвучивается: слот не резервируется и не запрещается.

## 👥 Распределение задач

### 1. AI, Голос и LLM
**Участники:** `@FreezeEngine`, `@semyoonov`, `@IGapone`
**Задачи:**
- Распознавание речи через Vosk (конвертация любого аудио формата в 16кГц WAV и транскрибация).
- Синтез речи через API Сбера (SaluteSpeech).
- Интеграция с GigaChat по API:
  - Системный промпт с передачей текущей даты, времени и дня недели (для обработки «завтра», «в пятницу»).
  - Описание схем тулзов (function calling): `create_task`, `create_meeting`, `list_events`, `search_events`.
  - Уточняющий диалог, если не хватает данных (например: «Поставь встречу с Иваном завтра» -> «На какое время поставить встречу?»).
- Оркестратор пайплайна: аудио/текст -> распознавание -> запрос в LLM -> вызов тулзов -> синтез речи -> ответ.

**Папки и файлы для работы:**
- `app/ai/stt/vosk_stt.py` — загрузка модели Vosk и распознавание речи.
- `app/ai/stt/audio_converter.py` — конвертер аудио (из Telegram OGG Opus / WebM браузера в 16кГц WAV).
- `app/ai/tts/sber_tts.py` — клиент синтеза речи SaluteSpeech.
- `app/ai/llm/gigachat_client.py` — клиент к API GigaChat.
- `app/ai/llm/prompts.py` — системные промпты и контекст времени.
- `app/ai/llm/tools.py` — описание схемы функций (tool calls) для GigaChat.
- `app/ai/llm/tool_executor.py` — обработчик выполнения тулзов (связка с репозиториями).
- `app/ai/assistant.py` — главный сервис ассистента, объединяющий все этапы.

- `app/repositories/user_repository.py` — репозиторий для пользователей.
- `app/repositories/event_repository.py` — методы создания, фильтрации по датам и поиска по событиям.
- `app/services/cache/redis_service.py` — клиент Redis и логика кэширования.
